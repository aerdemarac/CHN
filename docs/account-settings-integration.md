# Account Settings frontend

`account-settings.php` is a single root-level visual preview for patient, doctor, healthcare_staff and admin. Open `http://localhost/CHN/account-settings.php?role=patient`. Missing, invalid and array roles default to patient. URL role selects fictional presentation only; it never authenticates or authorizes. No sessions, cookies, account reads, network mutation calls, storage or database changes were added. A manually forged POST renders a no-changes notice and ignores submitted values.

The existing Top Bar discovers the root file automatically. Its account link now retains supported canonical role labels, and its title map includes Account Settings. Its layout/interactions and the Sidebar are reused. Admin sidebar settings.php remains separate. Medical Cases, Feedback and Dashboard code are untouched.

Personal information uses user schema names name, surname, email, phone, birth_date, gender and nationality. Required names/email and optional international phone, non-future birth date and two-letter nationality code are checked in the browser. Invalid fields get adjacent errors, aria-invalid and focus on the first failing control. National ID, internal IDs, passwords and hashes are not displayed. Role is display-only. Fixtures use example.invalid; do not enter real personal information.

Preferred languages reuse the actual Top Bar language map and order (tr/en/el/ru/yo/de/fr/es). Notification choices are illustrative draft controls; they do not imply delivery or existing preference columns. Theme remains light. Checking a draft reports that nothing is saved; Save and Change Password are unavailable. No password fields are requested without a secure workflow. Cancel restores all fictional form defaults and clears errors. Changed drafts trigger the browser's native leave/reload warning, when supported; successful validation does not mark drafts as saved. No-JavaScript submission buttons stay disabled.

Future integration requires verified account reads, an authenticated update interface, server-side validation and email uniqueness/verification policy, CSRF and appropriate account authorization, country/gender normalization, and a separately approved preferences storage contract (not currently in user schema). Identity and role must come from trusted authentication, never GET or editable form fields. A real password workflow requires current-password verification/reauthentication, server hashing and session handling. Replace draft-only interactions only once these contracts exist. No endpoint or database migration was invented.

Role refinements: Patient, Doctor and healthcare_staff email, birth_date and nationality are read-only, with visible labels, explanatory hints and muted CHN field backgrounds. Admin can edit all seven supported personal fields. Only Admin may edit those three fields; other personal fields retain their existing editing behavior for every supported role. Internal user_id, role changes and authorization settings remain outside this form. SMS reminders were removed; email reminders and preferred language remain.

Gender choices are Female and Male for every role. The dropdown is derived from the recorded value rather than a hard-coded selected gender. An absent or unsupported recorded value uses a disabled empty prompt and displays the current nonempty value separately. It is never implicitly converted to Female or Male. Reset restores the original selection. Integration must preserve the stored value when no explicit permitted replacement is submitted, including when an unrelated field is updated; do not normalize legacy values or NULL to a dropdown default.

Required server enforcement before enabling updates:
- Resolve identity and canonical role from authenticated server state, never the preview URL or submitted role. Authorize every update against that identity.
- Use explicit per-role field allowlists. Patient, Doctor and healthcare_staff updates must reject attempted email, birth_date or nationality changes even if readonly attributes are removed or a request is forged. Admin personal-account edits may include name, surname, email, phone, birth_date, nationality and gender; this does not authorize changes to user_id, role or privileged settings.
- Validate permitted values server-side, enforce CSRF protection and email uniqueness/verification policy, and preserve unchanged legacy gender values. HTML attributes and JavaScript are presentation/validation aids, never authorization.
- Keep saving disabled until these controls and persistence exist. The current PHP ignores all submitted account values for every role; no frontend edit or forged request can update a database through this page.

Initial refinement verification (before extending the read-only restriction to Doctor and healthcare_staff): headless Chrome passed PHP-rendered pages for all four roles at 393px and 1440px (eight combinations), including read-only/editable controls, gender choices and unchanged legacy selection, SMS absence, email preference, no horizontal overflow, shared shell, Top Bar dropdown and canonical account link targets, email/phone errors, first-error focus, draft-only feedback, reset, and form labels. These browser checks used local rendered files; live HTTP navigation was not exercised. PHP checks confirmed forged POST values are ignored for every role and supported/legacy/empty gender fixtures do not select an unintended replacement. PHP syntax and git diff --check passed. No assets were added or downloaded.

Follow-up verification: PHP-rendered controls confirm email, birth_date and nationality are read-only for Patient, Doctor and healthcare_staff, and editable for Admin. Name, surname and phone remain editable for all four roles. PHP syntax and git diff --check passed.
